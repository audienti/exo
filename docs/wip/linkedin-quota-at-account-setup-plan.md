# LinkedIn connection-request quota at account setup

Status: locked for implementation.
Created: 2026-06-11. Locked: 2026-06-11. Revised: 2026-06-11, 9 Codex plan review rounds applied (see Revision log). Claude called convergence at round 9; round 10 was not run.

The operator hit this during the Ali incident: a LinkedIn execution account was created and looked execution-ready, but `exo daily` would not compute invitation capacity until a weekly connection-request quota was manually written to the account. Today the CLI lets a LinkedIn account be created without that quota — silently for `users accounts map-runtime`, and as an optional flag for `users accounts add` — and the operator only discovers the gap when planner pressure surfaces `configure_connection_request_quota`. This plan closes the gap at the **interactive CLI surfaces** (`users accounts add` and `users accounts map-runtime`) so a LinkedIn account cannot land through those paths without either a stored weekly quota or a visible default + warning. The **non-interactive config import surface** (`importConfigBundle` at `src/core/import-config.js:108`) is out of scope for this plan — it parses bundled users directly and can land a quota-less account; treated as an accepted tradeoff for portable configs, with an explicit Non-goal and a follow-on candidate listed in Open questions.

## Current behavior (verified in code)

- Capacity is gated on a stored weekly quota. `build-outbound-capacity-view.js:320-372` emits `status: "needs_configuration"` with a planner item `kind: "configure_connection_request_quota"` whenever the governed LinkedIn account's `automationControls.weeklyQuotas.invitations` is null (`build-outbound-capacity-view.js:341`, `:351`).
- The signal is the only path the operator has into the fix today. `build-outbound-capacity-view.js:777-803` constructs a writeback command — `exo users accounts add ... --max-connection-requests <weekly-count> --json` — but the operator has to copy and run it; no other surface (UI, setup wizard, map-runtime output) prompts for the quota at account-creation time.
- `users accounts add` accepts `--max-connection-requests <count>` (`src/cli/commands/users.js:350`) but as an **optional** flag. When omitted, `buildAccountAutomationControlsFromOptions` returns `null` (`src/cli/commands/users.js:637-651`) and the account is written with `weeklyQuotas.invitations: null` (schema default at `src/schema/user.js:91`).
- `users accounts map-runtime` (`src/cli/commands/users.js:525-560`) does **not** accept any quota flag. It calls `mapUserRuntimeAccounts` (`src/core/map-user-runtime-accounts.js:28`), which calls `upsertUserConnectedAccount` at `:183-192` without passing `automationControls`. A first-time mapped LinkedIn account always lands with no quota.
- Update is safe today. `upsertUserConnectedAccount` merges existing weekly quotas with the input (`src/core/upsert-user-harness-connection.js:98`, `:111-117`), so re-running `users accounts add` for the same account without `--max-connection-requests` preserves the previously-set quota. The "preserve quota on update" concern from the incident retro is already covered for `users accounts add`; the same path runs from `map-runtime` and inherits the preservation behavior.
- Test coverage for the success path exists. `test/account-quota-capacity.test.js:88-196` asserts that:
  - `users accounts add` without quota → `daily.capacity.linkedin.status === "needs_configuration"` and `items[0].source.kind === "configure_connection_request_quota"` (`:132-146`).
  - Re-running `users accounts add` with `--max-connection-requests 125` flips daily to `configured` and persists `weeklyQuotas.invitations === 125`, with the preferred flag preserved (`:148-189`).
  - There is **no** test today that exercises `users accounts map-runtime` for LinkedIn → daily becomes computable, because map-runtime cannot set a quota.
- The signal is not surfaced in any UI affordance. `grep configure_connection_request_quota src/cli/exo-ui-server.js src/core/execute-action-intent.js src/artifacts/` returns nothing outside `build-outbound-capacity-view.js`. The planner item shows up in daily/next renderers, but the operator has no "set quota now" intent or form in the setup UI.

## Decisions

Locked by operator decision, 2026-06-11:

- **Default-on-missing for LinkedIn account add.** When `users accounts add --capability linkedin` is run without `--max-connection-requests`, the CLI writes a sentinel default into `automationControls.weeklyQuotas.invitations` and emits a warning on stderr naming the override flag. The same policy applies to `users accounts map-runtime` for first-time LinkedIn mapping (W2). **Why:** A required flag fails callers that already exist (including any script using the canonical example pattern), and warn-only-with-null reproduces the Ali incident — the account looks ready but isn't. Defaulting writes *some* working quota the planner can compute against, and the stderr warning gives the operator an explicit invitation to set the real number. The exact value is locked separately (see next Decision).

- **Default value: 125/week.** Daily target ≈ 25 invitations per business day. **Why:** Matches the canonical test value (`test/account-quota-capacity.test.js:165`, `:248`, `:382`), which is itself the operator's calibrated number for a warmed LinkedIn account. The operator owns the population of accounts and judges them as warmed-enough for 125 as a starting line; underuse from too-low defaults is the larger silent failure. The stderr warning still names the override flag so operators with a cold account can dial down with `--max-connection-requests 25` at add time. The default applies identically to `users accounts add` (W1) and `users accounts map-runtime` first-time mapping (W2).
- **Map-runtime override flag: single `--max-connection-requests <count>`.** Same spelling as `users accounts add` (`src/cli/commands/users.js:350`) and `profiles claim` (`src/cli/commands/profiles.js:145`). When supplied, it applies to whichever LinkedIn account map-runtime creates. When `--connector gmail` (or any non-LinkedIn-bearing scope) is supplied alongside the flag, the flag is irrelevant — emit a stderr warning that the flag was ignored so the operator does not assume it landed somewhere. **Why:** the flag name encodes its meaning ("connection requests" = LinkedIn invitations), it matches the idiom on the two sibling commands operators already use, and per-capability syntax is unjustified overhead while LinkedIn invitations are the only weekly quota that gates capacity. If other quotas need to be set at map-runtime time, they get their own flags (`--max-messages`, `--max-profile-visits`) — `render-browser-profile.js:22` shows the schema already treats them as distinct fields.
- **No UI work in this plan.** The user/account detail renderers already display `automationControls.weeklyQuotas.invitations` (`src/artifacts/render-user.js:12`); under the defaulted policy the planner item `configure_connection_request_quota` stops firing for new accounts (every fresh LinkedIn account lands at 125), and the W1/W2 stderr warnings are the most-noticed possible surface for the moment quota matters most — the moment the account is created. **Why:** The original W3 framing came from a pre-default world where missing-quota was a recurring planner symptom. Defaulting eliminates that symptom for new accounts. Adding UI affordances now solves a problem the defaulting just removed. Tradeoff: operators must drop to the CLI to override a defaulted quota; given LinkedIn quota changes are infrequent and the CLI command is one line, that friction is accepted. Revisit if evidence emerges that operators systematically miss the default warning.
- **Vestigial profile-claim quota flag removed.** `profiles claim --max-connection-requests` (`src/cli/commands/profiles.js:145`) is removed as part of this plan, with the example strings at `profiles.js:55` and `:155` updated accordingly. **Why:** Profile-backed LinkedIn is already blocked at the capacity layer (`test/account-quota-capacity.test.js:336-337` asserts `daily.capacity.linkedin.status === "unavailable"` with reason "profile-backed linkedin accounts are no longer supported"), so the flag persists a value the capacity logic ignores. An operator who uses it is silently misled into thinking they configured capacity. Closing the misleading surface alongside the gap-closing work in W1/W2 is a small cost for an internally consistent CLI. The schema field `profile.automationControls.weeklyQuotas.invitations` stays — existing values are preserved, just never read.

## Non-goals

- Changing the daily/weekly capacity math itself (`build-outbound-capacity-view.js:374-411`). The math is correct once a quota lands; this plan only ensures the quota lands.
- Auto-discovering the operator's LinkedIn weekly invite limit from LinkedIn itself. Out of scope; the operator names the number.
- Profile-backed LinkedIn accounts. They are already blocked (`build-outbound-capacity-view.js` returns `unavailable` for browser-profile sourceType per the test at line 336-337) and not part of this gap.
- ~~The connection-request *send* path. Whether sends respect the quota at send time is a separate concern.~~ **Corrected during round 1 review:** the dispatch gate already reads `senderAccount?.automationControls?.weeklyQuotas?.invitations` as the rolling weekly cap for `send_connection_request` at `src/core/outbound-dispatch-gate.js:481` (enforced by `evaluateRollingCaps` at `:237-245`). Defaulting missing quotas to 125 therefore also caps weekly sends at 125 for those accounts. This is an intentional side effect of unifying the capacity-planning and send-pacing source of truth — they were always meant to be the same field. Existing accounts that operated under a null weekly cap will gain a 125/week send cap the first time a quota-less `users accounts add` re-runs against them. Acceptance covers the dispatch-gate behavior post-defaulting (see Acceptance).
- InMail and message quotas. Today only `invitations` is the capacity-blocking field; messages and inmail are separate quotas with their own setup paths and are not part of the Ali incident.
- Config import (`exo config import` / `importConfigBundle` at `src/core/import-config.js:108`). The schema at `src/schema/user.js:88-94` and `src/schema/browser-profile.js:67` allows two problematic states for `weeklyQuotas.invitations` to land via a bundled config: (a) `null` (planner will surface `configure_connection_request_quota` on the next `exo daily`); and (b) the legacy value `0` (planner treats as configured-at-0/day while the send gate at `outbound-dispatch-gate.js:237` skips the cap as `< 1`, so sends are effectively uncapped — a silent dual-state failure neither surface catches). This plan does not change either case. The W1/W2 default does not fire because the import did not go through `users accounts add` or `users accounts map-runtime`. Listed in Open questions for follow-on work; the legacy-0 case is the more urgent of the two.

## W1: default the LinkedIn invitation quota at `users accounts add`

Why this matters: today the operator can run `users accounts add ... --capability linkedin` and the command exits successfully, but the user record is now in a state Exo refuses to plan against — `weeklyQuotas.invitations` is null and `daily` returns `needs_configuration`. The Ali incident hit this disconnect between "command succeeded" and "capacity is computable". Defaulting closes the gap by making the success path actually planning-ready, while the stderr warning gives the operator an explicit prompt to dial the number for accounts that need a different value.

Work:

1. In `src/cli/commands/users.js:339-427`, change the `users accounts add` action so that when ALL of the following are true:
   - `options.capability === "linkedin"`
   - the account is **harness-backed**, not profile-backed (i.e., `options.profile` is unset and `options.runtime + options.connector` are set — the action site already distinguishes these at `:361-367`)
   - `options.maxConnectionRequests === undefined`
   - **there is no existing stored invitations quota** for the same account on this user
   
   the CLI:
   - writes `automationControls.weeklyQuotas.invitations: 125` into the account, and
   - emits a stderr warning naming the override flag — for example: `"warning: no --max-connection-requests supplied for linkedin; defaulting to 125/week. Re-run with --max-connection-requests <n> to set a different value."`
   
   Profile-backed LinkedIn accounts (`users accounts add --capability linkedin --profile <id>`) do NOT get the default and emit no warning — they are blocked at the capacity layer per Non-goals, so writing a quota would mislead the operator the same way `profiles claim --max-connection-requests` did before W4 removes it. The harness-backed scope is the only path where the default is meaningful.
   
   **`--max-connection-requests` is also explicitly rejected on profile-backed `users accounts add`.** Today the action site at `:408-418` calls `buildAccountAutomationControlsFromOptions` regardless of source type, so `--profile <id> --max-connection-requests 25` would persist `weeklyQuotas.invitations: 25` onto a profile-backed account — the exact misleading surface this plan is closing on `profiles claim`. Reject the flag combination at the action site before calling `upsertUserConnectedAccount` with an actionable error: `"--max-connection-requests is not valid for profile-backed accounts. LinkedIn quotas are only configurable on harness-backed accounts (--runtime + --connector)."`. Add the rejection check after the existing profile/harness validation at `:361-367`.
2. The "no existing stored invitations quota" check is the load-bearing addition over the original draft. Without it, a quota-less re-add of a previously-configured account would overwrite a stored 25 with the 125 default (the merge at `src/core/upsert-user-harness-connection.js:111-117` puts the input last). The check must happen before computing `automationControls` and pass through to the helper. **Lookup key must mirror `upsertUserConnectedAccount`'s match function exactly** (`src/core/upsert-user-harness-connection.js:71-81`), not approximate it:
   - profile-backed (`options.profile` is set): match on `capability + browserProfileId`.
   - harness-backed with `options.providerAccountId`: match on `capability + providerAccountId`.
   - harness-backed without `options.providerAccountId`: match on `capability + harnessConnectionId`, resolved at `users.js:395-405`.
   - Handle is **not** part of the key — managed accounts can legitimately be re-bound to a new handle without losing their identity, and `upsertUserConnectedAccount` does not key on it. If the lookup uses handle, a handle change defeats preservation and the merge silently overwrites the prior quota. Run the lookup against `nextRaw.accounts` after the harness-connection upsert so `harnessConnectionId` resolves correctly. If found and `account.automationControls?.weeklyQuotas?.invitations` is a **positive integer (`>= 1`)**, do NOT default — write no `automationControls` and emit no warning. Re-run preserves. A stored `0` (possible from legacy data the schema's `.min(0)` at `src/schema/browser-profile.js:67` allowed before this plan) does NOT count as "existing-quota-present" — the send gate skips caps `< 1`, so a stored 0 is meaningless. Treat legacy 0 as missing and let the W1 default fire (writing 125) on the next quota-less re-add. The literal `"unlimited"` is not a valid stored value either — `parseQuotaValue("unlimited")` stores null, and null is by definition "no quota set" here.
3. The default is applied LinkedIn-scoped only. Gmail, hubspot, sales-navigator, and generic-web accounts pass through `buildAccountAutomationControlsFromOptions` (`src/cli/commands/users.js:637-651`) returning null and write no quota — no behavior change for those capabilities.
4. Implement by extending `buildAccountAutomationControlsFromOptions` to accept a second parameter `existingInvitationsQuota: number | "unlimited" | null` resolved at the action site. The helper returns `{ weeklyQuotas: { invitations: 125 } }` only when `options.capability === "linkedin"` AND `options.maxConnectionRequests === undefined` AND `existingInvitationsQuota === null`. Otherwise the existing return values stand. The action site is responsible for the lookup (W1 item 2) and for emitting the warning when the helper signals it applied a default (return shape: `{ controls, defaulted: boolean }`).
5. Define a single source of truth for the default value: a named export `LINKEDIN_DEFAULT_WEEKLY_INVITATIONS = 125` in **`src/core/user-account-defaults.js`** (new file). Both `src/cli/commands/users.js` (W1) and `src/core/map-user-runtime-accounts.js` (W2) import from this module. The constant must NOT live in `users.js` — that would force `map-user-runtime-accounts.js` to import from the CLI module, creating a core-from-CLI dependency cycle. Tests at `test/account-quota-capacity.test.js:165,248,382` continue to use the literal `125` so they pin the public default value rather than rubber-stamping whatever the constant happens to be.
6. Update the `addAccountUsage` example string at `src/cli/commands/users.js:56` and the inline option description at `:350` to document the default behavior: "Weekly quota for connection requests/invitations (positive integer). Defaults to 125 for LinkedIn on first add when omitted; re-adds preserve the previously stored value."
7. **Tighten `--max-connection-requests` to positive integers only on `users accounts add` and `users accounts map-runtime`.** Reject both `unlimited` and `0` at parse time with an actionable error suggesting `--max-connection-requests <positive integer>`.
   - `unlimited` rejection: `parseQuotaValue("unlimited")` returns `null` (`src/cli/commands/users.js:710-712`), which is the same in-storage representation as "no quota set" — capacity treats null as `needs_configuration` (`build-outbound-capacity-view.js:320`), so `unlimited` invitations was never workable through the planner. Under this plan a null value is also a target the defaulting overrides, which would silently overwrite an operator's intentional `unlimited` choice on the next quota-less re-add.
   - `0` rejection: `parseQuotaValue` accepts `0` today (the check at `:715` rejects `< 0`, not `< 1`), and `evaluateRollingCaps` at `outbound-dispatch-gate.js:237-239` skips caps `< 1` — so storing `0` would be silently treated as "no cap" at the send gate while reading as "0/week is the plan" at the planner. The two surfaces would disagree. Reject at parse time instead.
   - Implementation: add an invitations-specific strict parser that requires `/^[1-9]\d*$/` AND `<= LINKEDIN_MAX_WEEKLY_INVITATIONS` (defined in `src/core/user-account-defaults.js` next to the default). The matches: `1`, `25`, `125`, up to the ceiling; rejects `0`, `-1`, `1.5`, `12abc`, `unlimited`, `none`, `null`, empty, AND values above the ceiling. Today's `parseQuotaValue` uses `Number.parseInt` which silently accepts `12abc` (parses as 12) and `1.5` (parses as 1), and the schema at `src/schema/user.js:88-94` and `src/schema/browser-profile.js:67` has no `.max()` — so without the ceiling, a typo like `999999999999` becomes durable state and the dispatch gate would never enforce a meaningful cap. Set `LINKEDIN_MAX_WEEKLY_INVITATIONS = 500` — well above any realistic warmed-account weekly limit (LinkedIn's documented absolute ceiling is well under this), but low enough that typos like `1250` get caught. Call the strict parser from the `users accounts add` action site at `users.js:638` and from the new `users accounts map-runtime` parse site (W2 item 1) for `--max-connection-requests` specifically; other quota flags (`--max-profile-visits`, `--max-messages`) continue to call `parseQuotaValue` unchanged. Error messages: `"Invalid max-connection-requests: <value>. Use a positive integer (>= 1)."` for syntax failures; `"Invalid max-connection-requests: <value>. Maximum allowed is 500/week."` for over-ceiling values.
   - The same parsing path is used by other quota flags (`--max-profile-visits`, `--max-messages`); those keep `unlimited` and `0` support unchanged — only the invitations parsing surfaces the rejection.
8. The first canonical test at `test/account-quota-capacity.test.js:88-146` currently asserts `daily.capacity.linkedin.status === "needs_configuration"` after a quota-less `users accounts add`. That assertion inverts under this plan — daily becomes `configured` with `dailyInvitationsTarget === 25`. The test is rewritten in W3 item 1 rather than preserved.

## W2: default and override the quota through `users accounts map-runtime`

Why this matters: `users accounts map-runtime --apply` is the entry point operators use to wire an authenticated runtime into a user record — exactly the moment a fresh LinkedIn account first lands on a user (`src/core/map-user-runtime-accounts.js:183-192`). Today it writes no quota, so the operator immediately hits `needs_configuration` on the next `daily`. Mirroring W1's defaulted behavior closes the gap at the most upstream surface in the setup chain, and the explicit override flag lets the operator name a different number in one command instead of two.

Work:

1. Add `--max-connection-requests <count>` to the `users accounts map-runtime` option set at `src/cli/commands/users.js:528-532`. The option accepts a positive integer (`>= 1`). Same flag name as `users accounts add`. The literal `unlimited` is rejected per W1 item 7, and `0` is rejected per the W1 item 7 update (a 0 cap would be silently treated as no cap by `evaluateRollingCaps` at `outbound-dispatch-gate.js:237-239`, which skips caps `< 1`).
2. Thread the parsed value through `mapUserRuntimeAccounts` at `src/core/map-user-runtime-accounts.js:28`. Add `linkedinInvitationQuota: number | null` to the options bag at `:17-26` — null when the flag was not supplied, a positive integer otherwise. The shape excludes `"unlimited"` because that string is rejected at parse time.
3. Today the write-branch gate at `map-user-runtime-accounts.js:166` is `if (apply && action === "ready_to_map")`, which means existing managed accounts (`action === "already_mapped"` set at `:142-144`) skip the writer entirely — the `mapping_updated` label at `:204` is effectively unreachable on re-run. The new gate must enable writes for `already_mapped + LinkedIn + needs-write` cases (both `explicit_override` and `defaulted`). The exact gate expression is defined in item 4 below as the consequence of computing `quotaAction` BEFORE the branch decision.
4. Resolve `quotaAction` per mapping BEFORE the write branch, and use the same `quotaAction` value to decide whether to enter the write branch. The previous draft put `quotaAction` resolution inside the write branch, but the `preserved` case never enters that branch (it's an `already_mapped` no-op), so the field would never be set. New flow per discovered capability:
   - Add a new per-mapping field `quotaAction: "defaulted" | "explicit_override" | "preserved" | "none"` to the result objects at `src/core/map-user-runtime-accounts.js:212-232`. Default value for every mapping is `"none"` (any non-LinkedIn mapping, or any LinkedIn mapping in a blocked state — `connector_not_available`, `excluded_identity`, `session_unavailable`, `identity_unresolved`, `missing_handle` set at `:135-160`).
   - For LinkedIn mappings only (`capability === "linkedin"`), compute `quotaAction` before the write-branch decision:
     - Resolve the upsert match key (same key as W1 item 2): `providerAccountId` if `discoveredAccount?.providerAccountId` is set, otherwise the resolved `harnessConnectionId` for this `(probe.runtime, probe.connector)`.
     - Look up the about-to-be-updated account in `updatedUser.accounts` by that key (NOT by `selectExistingManagedAccount`'s result). The existing-managed-account from `selectExistingManagedAccount` is narrower; the upsert's match is the authoritative key.
     - Branch on `(linkedinInvitationQuota, existingAccountAtUpsertKey?.automationControls?.weeklyQuotas?.invitations)`:
       - **Explicit (non-null) `linkedinInvitationQuota`** → `quotaAction = "explicit_override"`. Write must happen.
       - **No explicit quota AND no existing non-null quota at the upsert key** → `quotaAction = "defaulted"`. Write must happen.
       - **No explicit quota AND existing non-null quota at the upsert key** → `quotaAction = "preserved"`. No write needed; the existing record is correct.
       - **Action is one of the blocked states (`connector_not_available`, `excluded_identity`, `session_unavailable`, `identity_unresolved`, `missing_handle`)** → `quotaAction = "none"` regardless of the flag. The blocking reason is the surfacing signal; quota work is not meaningful.
   - The write-branch gate at `:166` now reads: `if (apply && (action === "ready_to_map" || (action === "already_mapped" && capability === "linkedin" && quotaAction !== "preserved" && quotaAction !== "none")))`. This enters the write path for `explicit_override` and `defaulted` (whether ready_to_map or already_mapped), and skips for `preserved` and `none`.
   - Inside the write branch, when `quotaAction === "explicit_override"` pass `automationControls: { weeklyQuotas: { invitations: linkedinInvitationQuota } }` to `upsertUserConnectedAccount` (`:183-192`). When `quotaAction === "defaulted"` pass `automationControls: { weeklyQuotas: { invitations: LINKEDIN_DEFAULT_WEEKLY_INVITATIONS } }`. The merge at `upsert-user-harness-connection.js:111-117` writes the value.
   - Warning surfacing is a contract of the core helper, not just the CLI action site, because `mapUserRuntimeAccounts` is called from at least three places: `users accounts map-runtime` (CLI), `completeOnboardingUser` in `src/core/onboarding.js:207` (also reachable via the UI action-intent path at `src/core/execute-action-intent.js:166,714`), and any future call site. If the warning lived only at the CLI action site (`users.js:540-549`), onboarding via either CLI (`exo onboarding`) or UI (`/act completeOnboardingUser`) would silently default a LinkedIn quota — the same Ali-incident failure this plan is closing.
   - `mapUserRuntimeAccounts` returns an additional `result.warnings: string[]` array. Each entry in `result.mappings` with `quotaAction === "defaulted"` AND `apply === true` contributes one warning string: `"map-runtime defaulted LinkedIn quota to 125/week for <runtime>:<connector> -> <handle>. Re-run users accounts add ... --max-connection-requests <n> to set a different value."`.

The UI path (`executeActionIntent` writer `completeOnboardingUser` at `:166,713-722`) does NOT surface the warning to the operator in this plan — `runCompleteOnboardingUser` today returns only `{ ok, writer, message }` and the UI client at `src/lib/exo-ui-components.js:632` reads only `data.message` and stores `exo-flash` for a single success toast. This is recorded as a follow-on in Open questions; if UI operators systematically miss the default, the toast/banner work moves into a follow-on plan.
   - The `users accounts map-runtime` CLI action site (`users.js:540-549`) reads `result.warnings` directly (no onboarding wrapper) and emits each entry to stderr.
   - Dry-run mode (`apply: false`) populates `quotaAction` for operators inspecting `--json` output but `result.warnings` stays empty since no write occurred. The plain-text renderer at `renderUserRuntimeAccountMapping` (`src/artifacts/render-user.js:182-183`) is NOT updated to display `quotaAction` in this plan — the existing `action=... Reason: ...` lines stay as-is, and stderr/UI warnings cover the operator-visible surface. (If operator feedback later shows the plain-text view should expose `quotaAction`, that's a small follow-on.)
5. When `--max-connection-requests` is supplied but no LinkedIn capability mapping is in scope at all, emit a stderr warning that the flag was ignored. The detection has to separate "no LinkedIn in scope" (truly ignored) from "LinkedIn in scope but blocked" (a different problem the existing `mapping.reason` already surfaces). At the CLI action site:
