# Freshness-first signal retrieval pipeline

Status: locked for implementation.
Created: 2026-06-12. Locked: 2026-06-12 (after operator answered all 8 open questions + corrected the Apify/harvestapi Decision to use the existing LinkedIn browser-profile stack). Revised: 2026-06-12, 2 Codex plan review rounds + 1 operator answer pass applied (see Revision log).

The operator's signal pipeline today does no governed external retrieval — LinkedIn inbound sync at `src/core/inbound-linkedin-sync.js:15-43` only reads from the operator's own inbox surfaces (sent/received invitations, messaging inbox, profile views). When Reddit and external LinkedIn retrievers move into Exo per #34, they must NOT replicate the broad-topic-then-qualify pattern that Audienti's outer prospecting drifted toward. This plan adds a narrow, freshness-first retrieval pipeline that pulls from a governed watchlist, applies deterministic first-pass qualification, and surfaces ranked engagement signals directly into the operator's daily/next planner items with measured time-to-surface latency. Three lanes (engagement-hand-raisers, repeat-engagers, hiring-support-signals) feed one ranked output. Reddit is in-scope by design but deferred to W7 as a parallel-pattern lane; v1 lights up the LinkedIn lanes only so the contract is proven against a familiar surface before extending.

## Current behavior (verified in code)

- Inbound retrieval today is operator-inbox-only. `src/core/inbound-linkedin-sync.js:15-52` defines **six** LinkedIn surfaces (`linkedin-sent-invitations`, `linkedin-received-invitations`, `linkedin-messaging-inbox`, `linkedin-profile-views`, `linkedin-followers-list`, `linkedin-following-list`) and pulls them via `executeToolMethodSync` from `src/lib/tool-registry.js:154`. None of these retrieve external posts, comments, reactions, or third-party engagement.
- The tool-registry pattern is well-established. `src/lib/linkedin-tool-methods.js:44-75` registers methods via `ensureLinkedinToolMethodsRegistered()` calling `registerToolMethod(...)`. `executeToolMethodSync` at `tool-registry.js:154` is the only public executor today and **rejects Promise returns** — it is strictly synchronous. There is no async executor.
- **Inbound observations are the planner-feeding model, not cues.** `inboundObservationKindSchema` at `src/schema/inbound.js:49-77` enumerates 27 observation kinds, including `public_engagement_opportunity`, `public_reply_received`, `comment_thread_updated`, `catch_up_update_detected`, and `follower_added`. These are the *existing* enums that already model engagement-style signals. `recordInboundObservation` at `src/core/inbound-observations.js:55-106` is the recorder, parsing through `inboundObservationKindSchema` at `:63` before constructing the record. The cue surface (`recordInboundCue`, `inboundCueKindSchema` at `inbound.js:28-34`) is a narrow UI-state hint surface (`unread_message_badge`, `invite_badge`, etc.) — NOT the right seam for retrieved engagement signals.
- `buildDailyView` at `src/core/build-daily-view.js:35-49` reads `rawObservations`, feeds them to `buildInboundReviewView` at `:45`, and surfaces planner items via `buildInboundReviewPlannerItems` at `:100`. The `rawCues` field is optional at `:25` but not used for planner-item generation today. Observations are the surfaced channel.
- Planner items use a nested source shape: `source: { type, kind, ... }`, not a top-level `kind`. Verified at `build-daily-view.js:307` (`type: "outbound_capacity"`, `kind: capacity.plannerItem.kind`), `:372` (inbound review), `:443` (packet), `:605` (inbox), `:635`, `:665`. Every new planner item must follow this contract.
- Signals are first-class. `src/schema/signal.js:18-30` defines `signalSchema` with `id`, `name`, `question`, `scope`, `matchRule`, `audienceIds`, `observationMethods`, `status`. The surface enum (`signalObservationMethodSchema` at `:7-15`) accepts `google | sales-navigator | linkedin | company-site | news | manual | other` — Reddit and "linkedin-engagement" are not yet enumerated.
- Motion targeting is `motion.targetMap.accounts`, not `motion.targetCompanyIds`. Verified at `src/schema/motion.js:27-31` (`targetMapSchema = z.object({ accounts: ... })`) and `:65` (`targetMap: targetMapSchema`). Any qualifier rule that checks "is this poster's company in the motion's target list" derives the company set from `motion.targetMap.accounts` (via a helper named in W4).
- Action intents are dispatched through `executeActionIntent` at `src/core/execute-action-intent.js`. The switch around `:105-173` routes writers like `promoteInboundPerson`, `ignoreInboundObservation`, `assignMotionUser`. Approvals for new watchlist sources need a new writer here.
- Database writers use the JSON-payload pattern. `mutateUserById` at `src/db/database.js` (added in PR #39, merged to main 2026-06-12) is the canonical "BEGIN IMMEDIATE / reload / mutate / write" helper for user payloads. Watchlists need a sibling `mutateWatchlistById` in the same shape.
- No watchlist model exists today. Grep over `src/` for `watchlist`, `track`, `monitor` returns only `companies.js` and `target-account.js` (unrelated semantics). The watchlist needs a new schema + db table.
- No Apify/actor integration exists. Grep for `apify` or `harvestapi` over `src/` returns nothing. The plan introduces an async runtime; see W2.
- External-service tokens are read via dedicated modules, not a generic `app-config.js`. Pattern at `src/lib/workspace-settings.js:69-89` (workspace settings reader) and `src/lib/unipile-config.js:14-54` (Unipile credential resolution). Apify token resolution should mirror these patterns in a new `src/lib/apify-config.js`.
- CLI commands register explicitly via `src/cli/index.js:108-125` (each command's `registerX(program)` is called). New `exo watchlists ...` and `exo signals ...` commands need explicit registration there.
- No latency-measurement mechanism exists for inbound observations today. Schema at `src/schema/inbound.js` records `observedAt` but no `surfacedAt`. Freshness is currently invisible.
- No deterministic-first-pass-qualifier framework exists. Today `recordInboundObservation` writes the observation and `auto-promote-inbound-accepts.js` is the only auto-routing layer (narrow: promotes accepted-invitation observations to people). A more general rule engine doesn't exist yet.

Using cues would store data the planner never reads. The existing observation enum already covers most engagement semantics; the gap is two enum additions for repeat + hiring, which is W5's explicit work. Tradeoff: existing enum shape lacks fields the engagement-lane work needs (e.g., `engagementCount`, `discoveredAt`, `surfacedAt`); those land via additive schema extensions in W5, not by inventing a parallel store.

Three new methods: `linkedin.fetchWatchlistCompanyPostsViaBrowser` (for `linkedin-company` watchlist sources), `linkedin.fetchWatchlistAuthorPostsViaBrowser` (for `linkedin-poster`/`linkedin-creator` watchlists), `linkedin.fetchPostEngagementViaBrowser` (for the engagement-extraction pass on a fetched post). Exo already owns an authenticated LinkedIn browser session via the browser-profile system; using it for external content retrieval keeps the data path within the operator's existing identity (so visibility matches the operator's account, no third-party scraper rate limits) and avoids both the Apify vendor lock-in and the new async-executor complexity. Tradeoff: retrieval cadence is bounded by the operator's browser session availability (the LinkedIn browser pass already runs on a schedule — the new methods piggyback). Throughput per pass is lower than a dedicated scraper would be, but the freshness target ("tens of minutes" per the Non-goals) is easily met for the watchlist sizes principle 2 envisions (small governed lists, not broad discovery).

- **Execution path stays sync. The round-1 async-executor work is no longer needed.** All new tool methods register through the existing `registerToolMethod` with a sync `execute` and dispatch via `executeToolMethodSync`. The browser session itself is owned by the existing LinkedIn capture stack; the tool-method wrapper is the same synchronous shape as the existing six sync surfaces. **Why:** the operator's Q2 redirect drops the only async-bound transport (Apify polling). With browser-driven sync methods, no async path is justified. Tradeoff: large multi-page browser fetches block the executor for that pass; mitigated by chunking the retrieval into per-watchlist-source method calls (each call's wall-clock is bounded by the browser's per-page rendering time, not by a poll loop).

- **Watchlist is a new top-level entity.** Schema at `src/schema/watchlist.js` with `id`, `kind: "linkedin-company" | "linkedin-poster" | "linkedin-creator" | "reddit-source"`, `externalRef` (e.g., company URL or profile URL), `label`, `governance: "approved" | "pending-approval" | "rejected"`, `addedBy`, `motionIds: string[]` (which motions consider this watchlist source), `lastRetrievedAt`, `createdAt`, `updatedAt`. Stored in a new `watchlists` table mirroring the `companies`/`motions` shape. **Why:** principle 6 in the issue body (human gate where errors are expensive) requires "newly discovered sources/watchlist additions should require approval" — that's a first-class governance field. Attaching the watchlist to motions (rather than to user or to workspace) keeps the source list aligned with the operator's existing motion-scoping model. Tradeoff: yet another schema; offset by the schema being narrow and reusing existing patterns.

- **Freshness is measured per cue, recorded on the cue, surfaced in daily/next.** Add `discoveredAt` and `surfacedAt` to the inbound cue schema at `src/schema/inbound.js` (alongside the existing `observedAt`). `discoveredAt` is when Exo's retrieval saw the external event; `surfacedAt` is when the cue first appeared in a planner item. `observedAt` stays as the external timestamp (the post/comment/reaction time). `latencyMs = surfacedAt - observedAt`. The latency is surfaced in `build-daily-view.js` as a property on each engagement planner item so the operator sees "freshness 7m" alongside the item text. **Why:** acceptance criterion #4 in the issue body — "retrieval-to-operator latency is measurable and visible". Without the per-cue split, latency math averages across surfaces and loses signal. Tradeoff: schema change for cue records (additive — old cues with missing fields stay readable, the new fields are nullable).

- **Ranked output flows through existing planner item shapes — new `source.kind` values, not a new surface.** Two new planner item entries in `build-daily-view.js`, each using the nested-source contract verified at `build-daily-view.js:307,372,443,605,635,665`: `source: { type: "engagement_signal", kind: "hand_raiser", lane: "linkedin-engagement-hand-raiser" }` and `source: { type: "engagement_signal", kind: "repeat_engager", lane: "linkedin-engagement-repeat" }`. The hiring-support lane does NOT generate its own planner items — it tags signals onto existing engagement items as `context.hiringSupportEvidence: { hires: [...], window: "30d" }`, per principle 5 in the issue body. Engagement hand-raiser items have `priorityRank: 0.95`; repeat-engager items have `priorityRank: 0.85`. Both surface through `exo daily` and `exo next` (the existing operator loop), NOT through a separate `exo signals` surface — `exo signals retrieve` only runs the retrieval pass; planner items are read via `exo daily --json`. **Why:** the issue body says "output should be a ranked worklist, not just stored observations" — the existing daily/next view IS the operator's ranked worklist. Adding a separate "engagement dashboard" splits attention; piggybacking on planner items keeps one operator surface. Top-level `kind` would break the existing contract; nesting under `source` matches every existing planner item. Tradeoff: the existing planner-item-array contract grows by two `source.kind` values; existing kinds stay untouched.

- **First-pass qualifier = deterministic rules per lane, LLM classification deferred to a Slow lane.** Engagement-hand-raisers and repeat-engagers run a pure-code rule chain: recency window (default 7 days), fit gate (audience-fit match via existing `targetingProfile` schema), role/company constraint (regex on title + company-in-motion check), engagement count (1+ for hand-raisers, 2+ for repeat-engagers). Hiring-support similarly: recency 30 days, role contains "engineering" or "design" or "operations" depending on the motion's premise, requires a company-in-motion match. The pipeline does NOT call any LLM on the hot path. Ambiguous matches (e.g., a poster commented on a competitor's post but the poster's company isn't in the motion's target list) fall into a `pending-classification` cue with `status: "ambiguous"` for an operator review surface or a future Slow-lane LLM pass — not v1. **Why:** principle 3 in the issue body ("deterministic first-pass qualification"; "LLM classification only where ambiguity remains, not on the full hot path"). LLM-on-hot-path is the exact failure the Audienti pipeline had. The deferred Slow lane keeps the door open without binding v1 to LLM availability. Tradeoff: ambiguous cues sit until the operator reviews or a future Slow lane processes them; mitigated by surfacing the ambiguous count in `build-agent-status.js` so the queue is visible.

- **Approval workflow = new `approveWatchlistSource` and `rejectWatchlistSource` writers in `executeActionIntent`.** Both writers mutate the watchlist row's `governance` field. The pipeline only retrieves from watchlist rows with `governance === "approved"`. Newly discovered sources (e.g., a poster who commented on a competitor's post but isn't in the watchlist yet) get auto-inserted into the watchlist with `governance: "pending-approval"` and surface as a planner item (`kind: "approve_watchlist_source"`, `priorityRank: 0.75`). **Why:** "Newly discovered sources/watchlist additions should require approval" — principle 6. The approve/reject writers fit the existing `executeActionIntent` switch idiom (`:105-173`). Tradeoff: every discovery turn produces a "to-approve" queue; the operator must clear it.

- **Reddit lane (W7) deferred to v2 with lower priority than LinkedIn — locked by operator (Q1, 2026-06-12).** The schema, watchlist `kind`, and ranking contract all admit Reddit upfront so v2 only needs the source-specific extraction. When Reddit ships, Reddit hand-raiser planner items get `priorityRank: 0.80` (below LinkedIn hand-raiser at 0.95 and below LinkedIn repeat-engager at 0.85). Reddit timing is low-priority overall: LinkedIn must be proven and operating before Reddit work starts. **Why:** the operator's direct answer — Reddit hand-raisers are lower-priority signals than LinkedIn ones, and the move-to-Reddit itself is not a near-term need. Get LinkedIn going first.

- **Ambiguous items route to operator panel as a next-move planner item — locked by operator (Q2, 2026-06-12).** When the W4 qualifier returns `verdict: "ambiguous"`, the observation is recorded with `qualifierVerdict: "ambiguous"` AND a planner item is emitted with `source: { type: "engagement_signal", kind: "qualify_engagement_signal", lane }` at `priorityRank: 0.70`. The item's `recommendedAction` is "Choose the person this engagement belongs to (or skip): <poster> engaged on <source>; closest matches: <person 1>, <person 2>". The operator answers by clicking through to a person-pick UI (extends `executeActionIntent` with a new `resolveAmbiguousEngagement` writer at `src/core/execute-action-intent.js` — takes `observationId` + `resolution: { kind: "assigned" | "skipped", prospectId? }`). Assignment writes the prospectId back to the observation and flips `qualifierVerdict` to `"qualified"`; skip writes `qualifierVerdict: "rejected"` with `resolution: "operator-skipped"`. **Why:** the operator's answer — push the ambiguity into the operator's daily panel as a discrete decidable next-move, not a slow-lane LLM pass. Removes busywork by giving the operator a structured prompt instead of a free-form research task.

- **Watchlist is motion-scoped; duplicate approvals across motions are accepted — locked by operator (Q3, 2026-06-12).** A watchlist row references a single motion via `motionId` (NOT `motionIds[]`); the same external account that is relevant to two motions creates two watchlist rows, each independently approved. **Why:** the operator's answer — relevance is a per-motion judgment ("is this offer relevant for this prospect under this motion's premise?"). Cross-motion sharing would coerce a single approval signal where two judgments are required. Schema correction: W1 schema field changes from `motionIds: string[]` to `motionId: string`. Tradeoff: the operator approves the same external account multiple times when it's relevant to multiple motions — that's the intended cost.

- **Recency window defaults: hand-raiser 7d (configurable up to 14d for larger-deal motions), repeat-engager 7d primary + 30d rolling count, hiring-support 30d — locked by operator (Q4, 2026-06-12).** The 7d hand-raiser default is the v1 baseline; W4's qualifier accepts `recencyWindowDaysOverride` per-call so a longer-cycle motion can pass `14`. **Why:** operator answer; longer windows fit larger-deal cycles where the operator's time-to-act is itself longer.

- **Repeat-engager threshold = ≥2 prior engagements in rolling 30d. Not per-motion configurable in v1 — locked by operator (Q5, 2026-06-12).** **Why:** operator confirmed. Defer per-motion configurability until evidence of need.

- **Auto-watchlist discovery is predictive, not flag-everything — locked by operator (Q6, 2026-06-12).** W6 (rewritten below) scores each discovered author against motion fit BEFORE inserting them as `pending-approval`. Authors that don't meet the predictive threshold are dropped silently (logged for debug). **Why:** the operator's answer — discovery should answer "is this actually a good opportunity to engage someone who might eventually buy the product or service connected to this motion?" not "did we see this person?" Removing busywork is co-equal with asking the right question. The scoring is rich-deterministic (role match + company-fit + premise keyword match + post-content alignment); LLM is NOT on the v1 hot path per the issue body's principle 3. See the W6 rewrite below for the scoring contract.

- **Engagement-on-own-company is skipped — locked by operator (Q7, 2026-06-12).** When a poster's company matches the post's company-page (the poster is engaging with their own employer's content), the W4 qualifier drops the item with `reason: "self-engagement"`. No observation recorded. **Why:** operator confirmed. Employee-on-own-company engagement is not a buy signal.

- **Ambiguous observations expire after 90 days — locked by operator (Q8, 2026-06-12).** A nightly sweep (added to the existing inbound cleanup pass at `src/core/inbound-observations.js` or a new sweeper) marks observations with `qualifierVerdict === "ambiguous"` and `discoveredAt < now - 90d` as `qualifierVerdict: "rejected"` with `resolution: "expired"`. They no longer appear in `pendingClassificationCount`. **Why:** operator's answer; 90 days bounds the slow-lane queue size while giving operators ample window to triage.

## Non-goals

- Generic third-party value-give discovery (covered by #19, declared parent #1). The engagement-hand-raisers lane is narrower: it tracks who engaged with watchlisted posters, not who created adjacent content.
- Sales-Navigator-specific retrieval. The issue body cites LinkedIn watchlist surfaces; Sales-Nav-specific search/list pulls are out for v1.
- Streaming/real-time push. The retrieval cadence is polling (every N minutes per actor lane). Push-based webhooks are out for v1; the freshness target is "tens of minutes", not "seconds".
- Aggregating engagement counts across multiple operators or workspaces. Per the existing scope, watchlist + signals are operator-scoped. Cross-workspace signal aggregation is out.

## W3: Retrieval lane orchestration with governed source enumeration
