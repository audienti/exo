# UI coherence: one attention model, one action contract, one vocabulary

Status: locked for implementation.
Created: 2026-06-12. Locked: 2026-06-12. Revised: 2026-06-12, 8 Codex plan review rounds applied (see Revision log).

An SDR-perspective walkthrough of the interactive UI (an AI agent operating the product cold; no send or approve action was taken) reported nine confusion clusters: three surfaces give conflicting "what needs attention" numbers, action CTAs do not state what clicking them causes, the same prospect gets contradictory warmup guidance on different pages, the header search is decorative on most pages, internal vocabulary (motion codenames, truth enums, reconcile reasons) leaks untranslated, prospect counts disagree and people appear twice, the operator list is a wall of near-identical cards with no "why this person next", and `/motions` makes the codename feel more primary than the offer. The common root: operator work, agent work, analytics, and system telemetry share one undifferentiated vocabulary, and each surface computes its own numbers. This plan introduces one shared attention model for all headline counts, locks a single action-contract verb set, single-sources per-prospect engagement guidance, adds a display-layer vocabulary translation, and makes prospect inventory counts and identity reconcile.

Relationship to open tickets: W1 absorbs the "Unassigned" fix from #60; W4 implements the UI-rename half of #59 (the favicon half stays in #59); #61 (lifecycle panel layout, stage stepper) is adjacent and untouched here.

## Current behavior (verified in code)

Attention counts — three pages, four sets, one shared word:

- `/operator`'s headline renders `counts.decisions` under the label "queued": `src/artifacts/render-operator.js:82-86` (`<b>${c.decisions}</b> queued`). `counts.decisions` = decision-queue items minus handled/cleanup (`src/core/build-operator-view.js:201-203`) concatenated with planner due-now items (`src/core/build-operator-view.js:204-205`, counted at `:218-219`). The tester's "92 queued" is mostly planner items, labeled as queue.
- Planner items are due-now cadence items, excluding `inbound_review`/`outbound_capacity` sources and prospects with a queued public warmup: `src/core/build-operator-view.js:641-677`.
- `/queue`'s headline renders `counts.queue` under the same label "queued": `src/artifacts/render-queue.js:80-84`. `counts.queue` = `shapeQueue(agentQueue.items).length`, i.e. agent tasks with a non-null `action` (`src/core/build-operator-view.js:214,220` and `:529-531`). - `/workspace`'s pulse computes its own pair: `decisions` = decision-queue items minus cleanup (`src/core/build-workspace-rollup.js:76,83`) — without the planner concat, hence "0 decide" while operator says 92 — and `agentReady` = `agentQueue.itemCount` (`:84`), where `itemCount = annotatedTasks.length` (`src/core/build-agent-queue.js:800-804`), hence "6 ready" agreeing with `/queue` by coincidence of construction, not by shared code.

- The server computes yet another count for chrome: `queueCount` at `src/cli/exo-ui-server.js:1039` from `queue.count ?? queue.itemCount`.
- There is no shared selector: each builder counts its own arrays.

## Decisions

Locked by operator decision, 2026-06-12:

- **All headline counts derive from one shared attention model.** A single core module computes named buckets and per-bucket items; `/operator`, `/queue`, `/workspace`, and the nav badge render from it and never count arrays themselves. Why: today `/operator` renders `counts.decisions` under the label "queued" while `/queue` renders `counts.queue` under the same label, and `/workspace` computes both numbers a third way (citations above) — the tester could not tell whether they were overwhelmed, caught up, or waiting on automation. Consequence: `build-operator-view`, `build-workspace-rollup`, and `exo-ui-server`'s chrome count all re-point at the shared model.
- **CTA labels state outcomes; statuses are not dressed as actions.** Every clickable label names what will happen and when (navigates, records approval for the next agent pass, runs the agent now); status badges are visually and verbally distinct from buttons. Why: "Compose request" navigates, "Approve & queue" records approval, "Send — add & queue" does the same family of thing with a different verb, and "Queued for agent" is a status that reads like an action — the tester declined to click anything, which is the correct response to an ambiguous contract and the worst outcome for the product.
- **Per-prospect engagement guidance is single-sourced.** One verdict function decides whether warmup/hook framing is allowed, and every surface renders from it; persisted recommendations re-validate against the current verdict before display. Why: the operator card framed a stored post as the hook while the detail page's recomputed verdict said skip warmup — contradictory guidance destroys trust in all recommendations.
- **Internal vocabulary never reaches operator surfaces untranslated.** Motion codenames, truth enums, reconcile reasons, and internal motion names get display-layer translations; stored identifiers do not change. Why: the tester had to translate `gentle-ancient-lizard`, `QUIET`, and "page-budgeted full reconcile" before acting — the product should not require learning the implementation.
- **Two operator-facing buckets: Yours / Agent's (P1, revised).** Yours = anything that cannot proceed without the operator: decision-queue items, planner items whose next step is operator compose/approve, and blockers only an operator can clear (assignment, auth, missing channel). Agent's = everything the agent moves in the background: tasks ready on the next pass plus scheduled/cadence-held work, with ready-vs-scheduled shown as sub-detail, never as competing headline numbers. `/operator` leads with Yours and sections its list as top-next plus grouped remainder; `/queue` is the Agent's view (headline: Agent's total with a "ready now · scheduled" sub-breakdown); `/workspace` shows the pair. The word "queued" is retired from operator-facing headlines. Why: operator decision 2026-06-12, revised from a four-bucket model on reread — the operating philosophy is "the agent moves everything in the background; the UI tells me what's mine", and two buckets answer "am I overwhelmed or caught up" in one glance. The split rides seams that already exist in `collectPlannerActionItems` (`src/core/build-operator-view.js:641-677`). Consequence: the "92" splits — operator compose/approve planner items → Yours, agent-executable → Agent's; the model still computes ready/waiting/blocked internally and rolls them up.

- **Approval is a go signal: it auto-runs the agent (P2).** A successful draft approval immediately starts a background agent pass — the same pass "Run agent now" starts — unless one is already active, in which case the approval is picked up by the running/next pass. The approve toast states which case happened. CTA verbs move to the "Approve & send" family; the contract sentence says the agent starts working immediately (actual send still subject to send-mode, channel availability, and cadence gates, which are unchanged). Why: operator decision 2026-06-12 — approval should mean "go", not "wait for a scheduler"; the inertness of approval was half the tester's confusion. Consequence: the approval writers gain a post-write trigger into the existing pass runner; bulk review stays safe because each spawn attempt while a pass is active no-ops against the run lock; W2 gains one behavioral work item and the execution-semantics non-goal gets a trigger-only carve-out.
- **Motion display labels are derived, no schema change (P3).** One helper `motionDisplayLabel(motion)`: an explicit operator-set name wins; a name matching the generator's `adjective-adjective-animal` pattern against its word lists (`src/core/motion-support.js:300-310`) is treated as generated — a heuristic, since the schema stores no provenance bit; the accepted tradeoff is that an operator who deliberately names a motion in exactly that pattern sees the offer label instead, which is harmless. The derived label source is `offerThesis.sourceTitle` (`src/schema/offer-thesis.js:6`), falling back to the `offer.sourceUrl` domain (`src/schema/motion.js:40-43`); the codename renders only as secondary metadata. Why: operator decision 2026-06-12 — the offer-primary pattern is already proven in `renderMotionChoiceOption` (`src/lib/exo-ui-components.js:316-352`), and a new editable field would cost a migration plus an edit surface for marginal gain since motions can already be renamed. Consequence: W4 stays display-layer; this implements the rename half of #59, the favicon half stays in #59.
- **Telemetry vocabulary humanized in place (P4).** Per-item freshness stays on cards in plain words ("Verified · 2h ago", "Partial sync", "Not checked", "Sync failed", "No recent activity"); system-level reconcile detail stays on `/workspace` and `/connections`, reworded in plain language with the internal reason preserved in the tooltip; no telemetry moves onto or off any surface. Why: operator decision 2026-06-12 — "is this recommendation based on fresh data" is useful at the point of decision; the leak is the words, not the placement. Consequence: `truthTag`/`TRUTH_META` rewording is a single-point change; W4's telemetry items are wording-only.
- **Dedupe = matcher fix + exact-key cleanup + cross-motion annotation (P5).** Record-time matching adds normalized email ahead of the name+title fallback; a one-time idempotent cleanup merges exact-key duplicates (same LinkedIn URL or same normalized email within a motion-company); the same human legitimately tracked in two motions keeps separate records, and `/prospects` annotates such rows ("also in <motion>") instead of rendering silent twins. No operator-confirmed fuzzy-merge UI in this plan. Why: operator decision 2026-06-12 — exact-key duplicates are the observed bug (the Vikrant rows) and are mechanically safe to merge; fuzzy merges are rare until the matcher fix proves otherwise. Consequence: a `/prospects` row means a motion-scoped prospect record with person identity expressed by annotation, not row merging; the fuzzy-merge flow moves to Open questions with a revisit trigger.
- **Header search wires to `/prospects` (P6).** Where a topbar search renders, it is the real GET form submitting to `/prospects?q=`; the decorative-pill fallback is deleted, so any page without search config renders no affordance at all. The wired scope is the operator-workflow list pages enumerated in W2 item 7; secondary/system surfaces (onboarding, `/users`, `/settings`) stay searchless. Why: operator decision 2026-06-12 — the functional form already exists in `renderTopbarSearch` (`src/lib/exo-ui-components.js:957-964`) and pages merely fail to pass a config; wiring the workflow pages is cheaper than a new endpoint, and deleting the fallback guarantees no future route can show a fake control. Consequence: searching from any wired page lands on `/prospects` results; W2 item 7 owns the route list.
- **One inventory selector for pool counts (P7).** `/workspace`'s Prospect Pool figure adopts the same filtered inventory count `/prospects` reports (archived dead-end records excluded); the excluded-records delta is tooltip material, never a competing headline. Why: operator decision 2026-06-12 — two pages, one number; the 102-vs-100 gap was exactly the `shouldIncludeProspect` filter. Consequence: `buildStats` (`src/core/build-workspace-rollup.js:55-57`) consumes the shared selector instead of summing raw motion-summary counts.

## Semantics to lock

- **Yours** = work that cannot proceed without the operator (decision-queue items, planner items whose next step is operator compose/approve, operator-clearable blockers). **Agent's** = work the agent handles in the background (ready on next pass, scheduled, cadence-held). Internal sub-states (`ready`, `waiting`, `blocked`) exist in the model for detail rows, never as competing headline numbers. (Locked at P1.)
- Operator-facing headlines use only the two bucket labels; "queued" is retired from headlines (sub-state copy may say "ready now" / "scheduled"). No two pages may render different sets under the same label.
- Counts equality invariant: a bucket's number shown on any two surfaces comes from the same function evaluated over the same inputs at the same build; renderers receive counts, they do not compute them.
- Engagement verdict: exactly one object `{ available, engageable, reason, selectedTarget }` per prospect per build, produced by one exported function; "hook" framing is permitted only when `engageable` is true.
- Display labels: every motion reference on an operator surface renders a human label; the codename may appear only as secondary metadata.
- Approval is a go signal: a successful approval starts a background agent pass when none is active; otherwise the active/next pass picks it up, and the toast states which happened. (Locked at P2.)

## Non-goals

- Visual redesign, new pages, or layout systems. This plan changes labels, counts, grouping, and selectors — not the design language.
- Changing agent execution semantics (lanes, scheduling, send gating, verify/canary/live behavior). Only their presentation changes; the single exception is the P2-locked auto-run trigger after approval, which adds a new trigger for the existing pass, not a change to what a pass does.
- A cross-entity omnibox (companies, motions, messages). Search scope here is people/prospects routing only (P6).
- Prospect lifecycle panel layout and stage stepper (#61).
- Renaming stored motion names, ids, or the transition motion's marker name — translations are display-layer.
- Fixing reconcile/page-budget mechanics themselves — only how their reasons are worded and where they surface.
